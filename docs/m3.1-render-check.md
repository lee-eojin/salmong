# M3.1: Render check

**Status: box checks PASS; laptop check PENDING.**

M3.1 draws `SimView` from a replay. The check comes from plan section 8: at equal tick counts, `state_hash` equals headless at several render rates. The box proves it headless; the reference laptop proves it in Chrome on WebGPU, and shows the drawing.

## What the box covers

| Behaviour | Where |
|---|---|
| Render on, per-tick hashes equal `replay::hash_sequence` at 30, 60, 144 Hz, capped 10 Hz and irregular frames | `crates/salmong-game/tests/render.rs`, `hashes_match_headless_with_render_*` |
| `Scene`, `RouteDraw` and `BusDraw` equal the pure functions of `SimView`, the network and `BusTrack` every frame | `draw_data_matches_view_every_tick`, `bus_draw_uses_overstep_fraction` |
| 16 passengers per station, then a `+n` badge | `queue_cap_and_badge_hand_table` |
| Routes rebuild on a network change only, the scene on tick frames only, nothing while paused | `routes_rebuild_on_network_change_only`, `scene_rebuilds_only_on_tick_frames` |
| Drawn positions agree with `Fit` hit-testing | `camera_fit_agrees_with_input_fit` |
| Vertex counts, extents and colours | `geometry_hand_values` |
| Layer meshes follow the draw data; empty layers are hidden | `layer_meshes_follow_draw_data`, `no_sim_res_draws_nothing` |
| `?replay=demo` lines equal `hash_sequence`, and the picture freezes at tick 900 | `demo_lines_match_hash_sequence_and_freeze`, `demo_body_shows_every_kind`, `selects_demo_parses_query` |
| Expected lines and pixel samples for the laptop | `cargo run --locked -q -p salmong-game --example demo_expect` |

## Laptop procedure

Use the reference laptop and setup from [m0.3-webgpu-check.md](m0.3-webgpu-check.md), on the command-line route described there.

1. On the box, write the expected values: `cargo run --locked -q -p salmong-game --example demo_expect > expect.txt`. It prints six `salmong: replay tick=<t> hash=<16 hex>` lines, the done line, `grid 64 40`, and `sample <kind> <x> <y> <r> <g> <b>` lines in grid units for tick 900.
2. On the laptop, build the unit commit with `trunk build --release --offline` and serve `dist/` on port 8080.
3. Start a separate Chrome with its own `--user-data-dir` and `--window-size=1920,1080 --force-device-scale-factor=1 --force-color-profile=srgb --enable-webgpu-developer-features --enable-features=WebGPUDeveloperFeatures`. Keep the window visible: an occluded window halts the clock.
4. Open `http://localhost:8080/?replay=demo`. Vary the render rate with a `requestAnimationFrame` busy-wait injected before load (`Page.addScriptToEvaluateOnNewDocument`): 0 ms, about 40 ms and about 110 ms per frame. Read the achieved rate from the `frame=` field, not from the setting.
5. For each rate, collect the console lines. Each `tick` and `hash` must equal `expect.txt`, followed by `salmong: replay done tick=900`.
6. After the done line, capture a screenshot. Map each `sample` to a pixel with the letterbox `s = min(W/64, H/40)`, pixel `((W - 64 s)/2 + x s, (H - 40 s)/2 + y s)` for a `W x H` canvas, and compare within 3 per channel.
7. Open `http://localhost:8080/` without the switch: no replay line appears and the screen stays salmon.
8. Record the per-frame draw-call count (informational for M5.2).

## Pass conditions

- Startup as in M0.3: `isFallbackAdapter` is `false`, `backend: BrowserWebGpu`, no `DeviceLost`.
- At two or more render rates, all six hashes equal `expect.txt`.
- Every `sample` line matches its pixel, so stations, routes, buses and passengers are drawn in the right place and layer.
- Without the switch, nothing is drawn.
