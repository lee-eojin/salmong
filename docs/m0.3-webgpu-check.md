# M0.3: WebGPU check on the reference laptop

**Status: NOT_RUN.** It needs the reference laptop's GPU. LEJ runs this procedure and fills in [Results](#results).

The check comes from plan section 8. It passes when, on the reference laptop:

1. The app clears to the known colour, salmon `#FA8072`.
2. The app logs a WebGPU adapter.
3. The device is recorded in this file. Section 6 then uses that laptop as the perf reference.

## What the box already covers

The box has Chrome but no GPU. Chrome gives it a software adapter (SwiftShader) and cannot show a WebGPU canvas: a plain WebGPU page with no Bevy loses its device the same way. So the box checks startup, and the laptop checks rendering.

## Before you start

- Use the laptop that will be the reference machine, with stable Chrome.
- Match the section 6 setup, so the recorded laptop is the one perf runs on: 1920x1080 at device-pixel ratio 1, mains power, no other tabs.
- Install `rustup`, then the two tools at the versions `Cargo.lock` needs:

  ```sh
  cargo install --locked trunk --version 0.22.1
  cargo install --locked wasm-bindgen-cli --version 0.2.130
  ```

## Procedure

1. Open `chrome://flags/#enable-webgpu-developer-features`, set it to **Enabled**, and relaunch Chrome. Without this flag, Chrome reported `vendor` and `architecture` on the box but left `device` and `description` empty.
2. From the repository root on `main`, start the app:

   ```sh
   trunk serve --release
   ```

   Wait for `server listening`. The first build takes several minutes.
3. Open <http://localhost:8080/>, open DevTools (F12), select **Console**, and reload the page.
4. Find these two startup lines:

   ```text
   salmong: WebGPU adapter {"vendor":"...","architecture":"...","device":"...","description":"...","isFallbackAdapter":false}
   AdapterInfo { name: "...", ..., backend: BrowserWebGpu, ... }
   ```

   The first line comes from `web/index.html`. The second comes from Bevy and shows which backend the renderer uses.
5. Check the screen. The whole window is one flat salmon colour, with no scrollbars and no white strip.
6. Measure the colour. In DevTools, press Ctrl+Shift+P (Cmd+Shift+P on macOS), run **Capture screenshot**, open the PNG in an image editor, and sample a pixel near the centre. Expect `rgb(250, 128, 114)`.
7. Open `chrome://gpu` and copy the **WebGPU** row under Graphics Feature Status, plus the GPU and driver lines.
8. Set the flag from step 1 back to **Default** and relaunch Chrome.
9. Fill in [Results](#results), set the status at the top of this file, and open a PR. If the check fails, also add the first row of [Troubleshooting](#troubleshooting) that matches.

## Pass conditions

All of these must hold:

- `isFallbackAdapter` is `false`, and Bevy logs no software rendering warning.
- Bevy's line has `backend: BrowserWebGpu`.
- The console has no `DeviceLost` error.
- The sampled colour is `rgb(250, 128, 114)`. A difference of one or two per channel from colour management is fine. A clearly darker, paler, black or white result is a failure.

## Troubleshooting

| You see | It means | Next |
|---|---|---|
| "salmong needs WebGPU" and `salmong: no WebGPU adapter`, then a Bevy panic `Unable to find a GPU!` | Chrome offered no adapter. The panic is expected after that line | Read the WebGPU row in `chrome://gpu`. Update the GPU driver. If the GPU is blocklisted, record that: a forced override is not a pass |
| `isFallbackAdapter` is `true`, or Bevy warns about software rendering | Chrome fell back to a CPU adapter | Not a pass. Check `chrome://gpu` for why hardware acceleration is off |
| `Caught DeviceLost error`, then `Quitting the application` | The GPU process or canvas failed. The box always stops here, the laptop must not | Not a pass. Copy the log messages at the bottom of `chrome://gpu` |
| Startup lines look right, but the colour is wrong | Rendering or colour handling differs on real hardware | Not a pass. Record the sampled value. A paler or darker salmon suggests an sRGB mismatch |
| `description` is empty | The flag from step 1 is off | Repeat step 1 |

Example adapter lines, measured on the box, so `isFallbackAdapter` is `true` here:

```text
Flag off: salmong: WebGPU adapter {"vendor":"google","architecture":"swiftshader","device":"","description":"","isFallbackAdapter":true}
Flag on:  salmong: WebGPU adapter {"vendor":"google","architecture":"swiftshader","device":"0xc0de","description":"SwiftShader Device (Subzero)","isFallbackAdapter":true}
```

## Why the page and checks look this way

- `web/index.html` sets `display: block` on the canvas. An inline canvas leaves a baseline gap, which adds a scrollbar that narrows the canvas.
- `web/index.html` requests the adapter with `powerPreference: "high-performance"`. Bevy asks for the same preference, so the page logs the adapter Bevy gets.
- wgpu passes on only `description`, which Chrome leaves empty by default. The page logs the other adapter fields itself.
- The "no WebGPU in the browser" case in `scripts/check-webgpu-startup.mjs` loads the page from `salmong.test`. `navigator.gpu` only exists in secure contexts, and that origin is not one.
- `scripts/check-web-build.sh` runs `trunk build --offline`, so a missing tool fails the check instead of being downloaded.
