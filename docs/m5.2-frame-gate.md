# M5.2: Frame gate

**Status: box checks PENDING proof; laptop gate PENDING.**

M5.2 draws every kind as one quad batch with the shape chosen in the fragment shader, adds `?bench=stress&seed=1`, and runs the section 6 frame-interval gate in Chrome on the reference laptop at 1920x1080, device-pixel ratio 1.

## Renderer

- `salmong_game::render` builds 4 vertices and 6 indices per instance: centre and half extent in the positions, local corner and shape code in `UV_0` (`uv.x = lx + 4 * code`), colour in `COLOR`.
- `ShapeMaterial` (`Material2d`, `src/shapes.wesl`, fragment only, default mesh2d vertex stage) picks the shape: circle 0, triangle 1, square or solid quad 2, star 3. All four layers share one material, so a frame is 4 layer draws plus Bevy's one full-screen draw.
- This is quad batching: each draw has `instanceCount` 1.
- `render::hit` evaluates the same shape test on the CPU; `demo_expect` and `stress_expect` use it, and the M3.1 and M3.4 expect files are unchanged.

## The `?bench=stress&seed=1` body

Scenario: the M2.9 workload (64 stations on an 8x8 grid, station 63 is the only `Star`, ramp rate 100), `Balance::bench()`.

| Tick | Command |
|---|---|
| 0 | `AddRoute` for routes 0 to 7, each over the 63 non-hub stations |
| 1,050 + 300 k, k = 0 to 23 | `EditRoute 7`, hub on for even k, off for odd k |

- 8 buses are in service, the current rules maximum (`MAX_ROUTES` = 8, one bus per `AddRoute`). First-release play maximum is 4. `Balance::bench()` still starts with 32 buses, so 24 stay free.
- 32 buses in service is not measured until a bus-adding command exists.
- Ticks 0 to 900 at x1 are the 30 s warm-up. At tick 900 the bench sets x2; ticks 900 to 8,100 are the 120 s steady window. At 8,100 the clock pauses and the picture freezes.

## Line formats

```text
salmong: bench stress seed=<s> warmup=900 end=8100
salmong: bench tick=<t> hash=<16 hex> alive=<a> buses=<b> rev=<r> speed=<1|2> frame=<n>
salmong: bench steady tick=900
salmong: bench done tick=8100
```

One `tick=` line per multiple of 300. `alive` is queued plus riding passengers, `buses` counts buses in service, `rev` is the routing table revision, `speed` is the clock speed when the line is written.

## Laptop protocol

Section 6: Stable Chrome, 1920x1080 at device-pixel ratio 1, mains power, no other tabs, the M0.3 laptop.

- The built-in panel is 3456x2234 shown as 2056x1329 points (device-pixel ratio 2). Chrome starts with `--force-device-scale-factor=1 --window-position=0,0` and a window sized so that `innerWidth` is 1920 and `innerHeight` is 1080. The driver checks inner size, device-pixel ratio and canvas size before and after each run and reports no verdict otherwise.
- The forced scale factor is non-default. The page renders 1920x1080 device pixels; macOS then scales that surface to the panel, which is extra work on the same GPU.
- Page JavaScript injected by the driver records `requestAnimationFrame` timestamps and render-pass draw calls between the `steady` and `done` lines. Three fresh Chrome runs; the worst run gates. Pass: p95 at most 16.7 ms, p99 at most 20 ms, at most 20 draw calls per frame.
- A real tab switch during the bench re-checks Q11 (resume on return).
